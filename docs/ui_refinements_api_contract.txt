Common rules (unchanged from Phase 5 Slices 1-4, docs/phase5_slice4_api_contract.txt):
  - Session login + CSRF. Not logged in -> 401. No role -> 403. Wrong role
    for the endpoint -> 403. Everything in this contract is GET (others 405).
  - Lists: {count, next, previous, results}; page_size default 50, max 500.
  - Errors: {"detail": str, "errors": {field: [str]}}; 400 / 401 / 403 / 404
    (and 410 for C2 only).
  - Dates ISO "YYYY-MM-DD"; timestamps ISO 8601 with offset (IST); amounts
    2-decimal strings ("1070.50", "-35.00"); counts integers.
  - <module> is the lower-case slug (upi).
  - Backward compatible: every change ADDS fields, filters or endpoints.
    Nothing is renamed or removed. Every value below is made up.
  - Role checks stay on the server (api/base.py CAPABILITIES, the audit
    role check, the NPCI file role lists). No new capability is needed: the
    new endpoints use existing ones (noted per endpoint).
  - The app never sends anything to NPCI. Nothing here changes that.

The "reply" object (used by A3, A4, A5)
--------------------------------------
The NPCI reply a case carries NOW, with exactly the generator's precedence
(npci_files/generator.py, Amendment 2): the Checker-approved reply
(APPROVED / COMPLETED case), else the Maker's submitted one
(PENDING_APPROVAL), else the rule's suggestion (OPEN / IN_PROGRESS /
CLOSED_SUPERSEDED).
  "reply": {
    "reply_type": "DRC",            // DRC | TCC | RET | RRC | NEEDS_REVIEW | SETTLEMENT (section "Reply types")
    "reply_type_label": "DRC",
    "action_type": "DRC_102",       // ActionType value; "" when the rule has no default
    "action_type_label": "DRC reply 102 (customer reversed online)",   // "" when none
    "flag": "DRC",                  // DRC | TCC | RET | RRC, or null (not an SSKUPI reply)
    "code": "102",                  // numeric NPCI code, null when not known yet / not a reply
    "text": "Online Reversal",      // the code's description = what the SSKUPI
                                    // "specifyother" column would hold if a file were
                                    // generated now; null when there is no code
    "label": "DRC 102 - Online Reversal",
                                    // ready-made button / column text:
                                    //   reply with code:   "<flag> <code> - <text>"
                                    //   code not known:    "RET (code not known yet) - <text>"
                                    //   not an SSKUPI reply: the action label
                                    //     ("Adjustment entry in CBS")
                                    //   nothing chosen:    null
    "source": "RULE",               // RULE | SUBMITTED | APPROVED (npci_files ReplySource)
    "source_label": "The rule's suggested reply"
  }

Reply types (the queue tabs, item 6.1) - a partition, every case is in one:
  SETTLEMENT    case_type SETTLEMENT.
  DRC/TCC/RET/RRC  a transaction case whose reply (above) has that flag:
                DRC_102/103/104 -> DRC; TCC_102/103 -> TCC; RET -> RET;
                MANUAL_CREDIT_RRC_501, RRC_501_NO_CREDIT -> RRC.
  NEEDS_REVIEW  every other transaction case = the reply is NOT an SSKUPI
                reply, i.e. a person must look at it:
                - the rule has no default reply: R07b / R07x (chargebacks),
                  R07c, R13, R14-R17, R99, and any rule added later without one;
                - or the reply chosen is not an NPCI file reply: CBS
                  adjustment entry (R12's default), chargeback raise / accept /
                  represent, refund customer, close without action.
  NOTE: the "needs review" FLAG (case flagged after a re-run, flag=needs_review)
  is a different thing and is NOT used for the tabs; such a case stays in its
  reply's tab and carries flags.needs_review = true. (Owner question Q1.)

A. U2 - THE DAY'S FLOW AND THE SSKUPI FILE EVERYWHERE
--------------------------------------------------------------------------------

A0 Date status (used by A1 and A2)
   One plain status per business date, computed from data the date overview
   already reads (reconciliation/overview.py), first match wins:
     RUNNING            a reconciliation run of the date is QUEUED or RUNNING.
     WAITING_FOR_FILES  the date was never reconciled (no rule evaluation),
                        or files were uploaded after the last reconciliation,
                        AND at least one expected file slot is not LOADED
                        (missing, still processing, waiting for the CBS date,
                        or failed).
     READY_TO_RUN       never reconciled, or files uploaded after the last
                        reconciliation, and every expected slot is LOADED.
     CASES_OPEN         reconciled, no newer file, and the date has active
                        cases (OPEN / IN_PROGRESS / PENDING_APPROVAL /
                        APPROVED; transaction and settlement cases).
     FILE_PENDING       (owner Q2, 2026-10-27) reconciled, no newer file, no
                        active case, but the SSKUPI step is not finished:
                        reply rows still wait for a file (the generator's
                        plan for the date has rows), OR a file of the date
                        (any sequence, _2 included) was never downloaded.
                        Label "SSKUPI file to generate / download".
     DONE               reconciled, no newer file, no active case, nothing
                        waits for a file and every file of the date has been
                        downloaded at least once. A date with nothing to send
                        at all (no DRC / TCC / RET / RRC reply rows, so no
                        file) is DONE without a file.
   "Reconciled" = a RuleEvaluationRun exists for the date. "Files uploaded
   after" = any current file of the date has uploaded_at later than the
   latest rule evaluation's started_at.
   Fields added:  "status": str, "status_label": str,
                  "status_detail": str   // one plain sentence, e.g.
                     "3 expected file(s) are not loaded yet." /
                     "Files changed since the last run; run again." /
                     "12 case(s) open." /
                     "All cases worked. 4 reply row(s) wait for the SSKUPI file:
                      generate SSKUPI14072026_2.csv." /
                     "All cases worked. Download SSKUPI14072026.csv." /
                     "No case open; SSKUPI file(s) generated and downloaded." /
                     "No case open; nothing to send in an SSKUPI file."
                   A DONE / FILE_PENDING sentence may end with
                     " 2 reply row(s) cannot go into a file yet (see the SSKUPI
                      preview)."  (rows the generator leaves out, e.g. no
                      numeric code: they do not block DONE but are named), and
                   any status may end with " The last run failed: <error>."
   The same status is returned by the dates list, the date detail and the
   home "day" block. Modules without an NPCI file format (IMPS later) never
   get FILE_PENDING. Cost: the generator's plan is built only for dates that
   would otherwise be DONE and still have a reply case in no file (one query
   finds them for the whole page), so a page of finished dates stays cheap.

   NOTE (dev data): the 172 files on the dev database were loaded from the

   Roles: Administrator, Auditor (audit.view), like the other audit lists.
   One timeline of case events, settings events, logins and operations,
   newest first (ordering=created_at for oldest first), paged.
   Filters (all optional; same meaning as the existing audit lists):
     date_from, date_to   inclusive IST dates on created_at
     user                 username, case-insensitive
     source               csv of case_event, settings_event, user_activity,
                          operation (the four existing tabs)
     event_type           csv; any value of the four lists' event types
                          (/audit/meta/); each applies to the source(s) it
                          belongs to, and a source with none of the given
                          types is left out
     module               slug; logins have no module, so with a module
                          filter logins are left out
     ordering             -created_at (default) | created_at
   GET /api/v1/audit/meta/ gains "everything_sources": [{"value", "label"}]
   (the source filter choices).
   Row:
   {
     "id": "case_event:9876",          // unique across sources; settings events are
                                       // "settings_event:<kind>:<id>" (kind as /audit/settings-events/)
     "source": "case_event",           // case_event | settings_event | user_activity | operation
     "source_label": "Case event",
     "event_id": 9876,
     "created_at": timestamp,
     "module": "upi" | null,           // null for logins
     "username": "chk1" | null,        // null = the system
     "event_type": "APPROVED", "event_type_label": "Approved",
     "summary": "chk1 approved reply DRC 102 - Online Reversal on case #4512",
     "link": "/upi/cases/4512" | null,
     "details": { the row exactly as the source's own list returns it
                  (/audit/case-events/, /audit/settings-events/,
                  /audit/user-activity/, /audit/operations/) }
   }
   Summary sentences (server-made, plain, no amounts):
     case events   "<user> took case #N", "... submitted reply DRC 102 -
                   Online Reversal on case #N", "... approved reply ... on case
                   #N" (+ " (self-approved)"), "... rejected reply ...", "...
                   marked case #N done", "... added a remark on case #N",
                   "The system created case #N", "The system changed the rule on
                   case #N from R13 to R01", ...
     settings      "<user> proposed / approved / rejected <item>", e.g.
                   "chk1 approved the response code change 'Edit: DRC 102 -
                   Online Reversal'"; "NTSL mapping v3 was retired (replaced)"
     logins        "ops1 logged in", "ops1 logged out", "Failed login for ops9"
     operations    "ops1 uploaded <file> for 14 Jul 2026", "ops1 started
                   reconciliation run #41 for 14 Jul 2026", "chk1 generated
                   SSKUPI14072026.csv (12 rows)", "ops1 downloaded
                   SSKUPI14072026.csv", "ops1 downloaded the original file
                   <file>", ...
   Performance: one UNION ALL of (source, id, created_at) over the six
   tables with the filters applied in each branch, ordered and LIMITed in
   the database (created_at is indexed on the large tables), then one query
   per source for the page's rows only. The total "count" is a COUNT over
   the same union.
