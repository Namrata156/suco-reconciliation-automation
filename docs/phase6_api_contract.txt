Who builds what:
  - Slice 6.1 (built now) uses ONLY existing endpoints: GET /api/v1/me/ and
    GET /api/v1/<module>/dates/ (date_from, date_to, ordering, page,
    page_size). Nothing below is needed for it.
  - Slices 6.2-6.4 use the endpoints below. The frontend builds the screens
    against this contract with test data and wires them up as each lands.

Common rules (unchanged from Phase 5, Slice 4 contract "Common rules"):
  - Session login + CSRF. Not logged in -> 401. No role -> 403. Wrong role
    for the endpoint -> 403. All report endpoints are GET only (others 405).
  - Lists: {count, next, previous, results}; page_size default 50, max 500;
    ?page=N&page_size=N.
  - Errors: {"detail": str, "errors": {field: [str]}}; 400 / 401 / 403 / 404.
  - Dates ISO "YYYY-MM-DD"; timestamps ISO 8601 with offset (IST); amounts
    2-decimal strings ("1070.50", "-35.00"); counts integers.
  - "csv" filters accept comma lists (priority=HIGH,MEDIUM).
  - <module> is the lower-case slug (upi), as in /me modules[].slug.

Report rules (new, apply to every endpoint in section B):
  RR1 Date range. date_from / date_to are INCLUSIVE.
      - On the BUSINESS DATE for B1-B4 and B8.
      - On the DECISION timestamp (IST date) for B6 (R7), and on the event
        timestamp (IST date) for B7.
      - Both omitted -> the current month (1st of this month .. today, IST).
        One omitted -> 400 errors.{date_from|date_to}: ["Give both dates."]
      - date_to before date_from -> 400 errors.date_to.
      - At most 92 days -> else 400 errors.date_to: ["At most 92 days per
        report; narrow the dates."]. Exception: B3 with group_by=month allows
        24 months (dates are widened to whole months).
      - The range actually used is echoed in "report.filters" (below).
  RR2 Every JSON answer carries a "report" block:
        "report": {
          "key": str,                    // "reconciliation", "settlement", ...
          "title": str,                  // "Daily reconciliation report"
          "module": str | null,          // slug; null for B7
          "filters": object,             // the filters applied, normalised
                                         // (dates filled in, csv split to lists)
          "generated_at": timestamp,     // "figures as of" on screen
          "generated_by": str,           // username
          "versions": {                  // what the figures were produced with,
            "rule_sets": [str],          // distinct values in the range; [] if n/a
            "ntsl_mappings": [str],
            "tolerances": [str]
          }
        }
  RR3 Every JSON answer that can be exported carries an "export" block, so
      the screen can label the button and refuse big downloads up front:
        "export": {
          "formats": ["xlsx", "csv"],    // what THIS server can write now.
                                         // ["csv"] until openpyxl is approved
                                         // by IT (R1 fallback). The SPA shows
                                         // "Download Excel" when "xlsx" is
                                         // present, else "Download CSV".
          "row_count": int,              // rows the export would hold (main sheet)
          "limit": 100000,
          "allowed": bool,               // row_count <= limit
          "sheets": [{"key": str, "label": str, "row_count": int}]
        }

A. DOWNLOADS (R1, R8, R10) - one parameter on every report endpoint
--------------------------------------------------------------------------------
Parameter: export=xlsx | csv          (omit = the JSON answer)
           sheet=<key>                (csv only; default = the first sheet)

  NOTE: deliberately NOT "?format=xlsx" (the design draft's wording). DRF
  reads ?format= as its renderer override (URL_FORMAT_OVERRIDE) and answers
  404 when no renderer matches, before the view runs. "export" avoids that
  without changing DRF settings. (BE: confirm, or set URL_FORMAT_OVERRIDE
  = None and keep "format".)

  - Same filters as the JSON answer; no paging (page / page_size ignored).
  - 200: the file, streamed.
      xlsx: Content-Type application/vnd.openxmlformats-officedocument.
            spreadsheetml.sheet; ALL sheets of the report in one workbook.
      csv:  Content-Type text/csv; charset=utf-8; ONE sheet per file
            (sheet=...), UTF-8 with BOM, CRLF line ends (Excel opens it
            correctly).
      Content-Disposition: attachment; filename="<file name>"
      File name: <MODULE>_<report key>_<date_from>_to_<date_to>[_<sheet>].<ext>
        e.g. UPI_exception_report_2026-07-14_to_2026-07-31.xlsx
             UPI_settlement_2026-07-01_to_2026-07-31_cycles.csv
        (B5 ageing: UPI_ageing_as_of_2026-10-23.xlsx;
         B7: user_activity_<from>_to_<to>.xlsx)
  - 400 errors.export:
      ["Excel download is not available on this server; use CSV."]
        (export=xlsx while openpyxl is not installed)
      ["<n> rows is more than the 100,000 a download may hold; narrow the
        filters."]  plus top-level "row_count": int, "limit": 100000
      ["Unknown export format."]
    400 errors.sheet: ["Unknown sheet; allowed: dates, rules"]
  - Every successful download is written to core.OperationLog as a NEW
    event type REPORT_EXPORTED, label "Report downloaded", details:
      {"report": key, "format": "xlsx"|"csv", "sheet": key|null,
       "filters": <same as report.filters>, "row_count": int,
       "file_name": str}
    module = the report's module (null for B7), business_date = null.
    It appears in GET /api/v1/audit/operations/ (event_type=REPORT_EXPORTED,
    link null) and in /api/v1/audit/meta/ operation_types. Refused downloads
    are not logged. (BE: confirm.)

  File content rules (both formats unless stated):
  - Header block first: bank, module, report title, filters, produced by,
    produced at (IST), versions (RR2). Then one blank row, then the table
    with a header row.
  - RRNs are text, never numbers. xlsx: string cells. csv: written as
    ="<rrn>" so Excel keeps all digits (a fixed server-made shape, not user
    text). (BE: confirm; the alternative is a leading apostrophe, which
    Excel shows in the cell.)
  - Text cells (remarks, reasons, names) starting with = + - @ TAB or CR
    are prefixed with an apostrophe (formula injection). Amount and count
    cells are numbers and are never prefixed (negative amounts stay -35.00).
  - Amounts: xlsx numbers, format #,##,##0.00 (Indian grouping); csv plain
    "1070.50". Dates: xlsx real dates shown dd-mmm-yyyy; csv ISO.
  - xlsx is written with openpyxl in write-only mode (streamed).

  How the SPA downloads: fetch() with the session cookie, then save the
  Blob under the Content-Disposition name. A 400 is shown as its message;
  a 401 starts the normal "session ended" flow. No plain <a href> links,
  so a refusal never lands the user on a JSON page.

   Filters: date_from, date_to (RR1); open_cases_only=true|false;
            ordering = "-business_date" (default) | "business_date";
            page, page_size (default 31, max 92).
   One row per business date that has anything (same set of dates as
   GET /dates/ in the range).
   Row:
   {
     "business_date": date,
     "files": {"expected": int, "present": int, "missing": int,
               "received": int},
     "match_groups": {"total": int,
                      "by_status": {"MATCHED": int, "UNMATCHED": int,
                                    "PENDING_RULE_EVALUATION": int},
                      "on_us": int, "cbs_reversed": int},
                      // (BE: on_us / cbs_reversed from TransactionMatchGroup
                      //  flags - confirm they are cheap per date, else drop)
     "results_by_category": {<status_category value>: int},  // meta.status_categories
     "rule_counts": {<rule code>: int},       // RuleEvaluationRun.rule_counts
     "cases": {"created": int, "open": int},  // open = ACTIVE_STATUSES
     "settlement": {"status": "TALLIED"|"UNEXPLAINED"|"NOT_READY",
                    "unexplained_amount": str} | null,
     "rule_evaluation": {"id": int, "rule_set": str, "finished_at": timestamp|null,
                         "triggered_by": str} | null,
     "last_run": {"id": int, "status": str, "requested_by": str,
                  "finished_at": timestamp|null} | null,
     "links": {"results": str | null,         // "/upi/dates/2026-07-14/results"
               "settlement": str | null,      // null when no settlement result
               "date": str}                   // "/upi/dates/2026-07-14"

     "rule_codes": [str],          // every rule with a count in the range, rule order

C. CHANGES TO EXISTING ENDPOINTS
--------------------------------------------------------------------------------
C1 /api/v1/me/ "permissions" - three NEW capabilities (api/base.py
   CAPABILITIES):
     "reports.view"           all five roles   (Reports page, B1-B5, B8)
     "reports.approvals"      Administrator, Auditor, Checker   (B6, B6s)
     "reports.user_activity"  Administrator, Auditor            (B7)
   Until they exist, the SPA (Slice 6.1) falls back to:
     reports.view           -> "results.view"   (same five roles)
     reports.approvals      -> "audit.view" OR "cases.approve" (= A, U, C)
     reports.user_activity  -> "audit.view"     (A, U)
   The fallback is used only while the key is ABSENT from /me; once the
   server sends it, its value wins. The SPA never treats the menu as the
   permission: the endpoints must check the role themselves (403).

C2 GET /api/v1/<module>/cases/ - new filter ageing_bucket (csv of
   meta.ageing_buckets[].label) for the ageing report cell links.
   (BE: if labels with spaces are awkward, add a "value" to
   meta.ageing_buckets and use that in both places.)

C3 core.OperationLog - new type REPORT_EXPORTED (section A); listed in
   /api/v1/audit/meta/ operation_types.

C4 ProposedAction - index on decided_at (design 6; no API change).

Not changed: GET /api/v1/<module>/dates/ keeps its shape; Slice 6.1 uses it
as is (page_size 31 on the all-dates screens).
