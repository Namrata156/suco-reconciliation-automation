PROPOSED DESIGN
--------------------------------------------------------------------------------
  S1 NTSL line classification. Each NTSL description maps to a category,
     held as DATA (a versioned mapping table) and never parsed in code:
       - TXN_REMITTER, TXN_BENEFICIARY (each with an RB variant)
       - FEE, FEE_GST, SWITCHING_FEE, SWITCHING_FEE_GST, PSP_FEE,
         PSP_FEE_GST, REBATE, REBATE_GST
       - ADJUSTMENT, PENALTY, COMPENSATION
       - SUBTOTAL, SETTLEMENT_AMOUNT, FINAL
     An unmapped description is flagged and never silently ignored.
     Changing the mapping goes through maker-checker, like the code table.

  S2 NTSL self-check per cycle: the sum of the categorised lines must
     equal NTSL's own Sub Totals / Settlement / Final lines. This catches
     a bad file or a bad mapping before any comparison.

  S3 Settlement reconciliation per business date and per cycle:
     - The system side is built from the rule results and the matrix,
       per category: matched remitter / beneficiary amounts, RB, on-us,
       DRC, Timeout, Adjustment.
     - A matched transaction gets its cycle from its NPCI row's
       settlement cycle; CBS has no cycle.
     - Compare with NTSL per category and compute the differences the
       spec lists: debit/credit, adjustment, fees and GST, penalty,
       final.
     - Fees, GST and penalties have no CBS transaction counterpart. They
       are validated as NTSL-internal totals, plus a CBS GL total if ops
       confirms which GL carries them (question Q3).

  S4 Gap explanation. The difference is attributed to named transactions
     (SOP: Timeouts not credited, DRCs not reversed, plus whatever the
     real data shows). The result shows "explained" and "unexplained"
     amounts.
     - TALLIED: the unexplained amount is 0, or within the permissible
       difference.
     - Otherwise a SETTLEMENT EXCEPTION.

  S5 Settlement exceptions use the Phase 3 exception queue as a new
     case type: one case per business date (and cycle if Q2 says so). It
     carries the calculation snapshot and the contributing transactions,
     goes through maker-checker, and is audited the same way.

  S6 NPCI File Generation (second half of Phase 4). After the checker
     approves an action (Phase 3), the system builds the NPCI bulk-upload
     file (DRC / TCC / RET / RRC / chargeback) for ops to upload to the
     NPCI portal. Once generated, a file is immutable and kept with its
     checksum and approver. BLOCKED: we have no NPCI upload file format
     (question Q5).
