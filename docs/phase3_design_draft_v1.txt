What the spec says:
  - Exception Management. Display unresolved exceptions, assign priorities,
    track ageing, allow remarks, track resolution status (spec "Exception
    Management"). Tracking, ageing, remarks, assignment and resolution
    (architecture table).
  - Maker-Checker. A maker generates reversal requests, a checker
    approves, unauthorised uploads are prevented, and approval history is
    recorded. "The final operational action shall be subject to the
    Maker-Checker Workflow" (Exception and Action Classification).
    Changes to rules, error codes and action mappings need authorised
    approval (Rule Versioning).
  - Roles. Administrator (users, rules, settings); Operations User
    (upload, run reconciliation, reports); Maker (review exceptions,
    prepare adjustments); Checker (approve or reject, authorise NPCI
    uploads); Auditor (logs, reports, approval history).
  - Auditability. Every reconciliation activity is logged.

  D3 Four-eyes. The same person may be maker and checker on one item if
     they hold both roles (small team).
     Mitigation proposed in P4 below.
  D4 R06b carry-forward. A refund/RET where CBS already shows the money
     back: decided by the owner with web research (owner asked PM to
     decide).
     - YES. The checker may approve "reply RRC 501 without a new credit".
     - The maker MUST attach the CBS reversal already posted (date,
       amount, RRN) as evidence.
     - It is never automatic.
     - Basis: NPCI RRC circular 38/2017-18. The remitter bank checks that
       a matching debit exists in CBS before crediting, and confirms 501
       only once the reversal is done in CBS. In R06b it already is, so a
       second credit would pay the customer twice.

--------------------------------------------------------------------------------
2. CASE LIFECYCLE
--------------------------------------------------------------------------------
  OPEN --take--> IN_PROGRESS --submit--> PENDING_APPROVAL
                     ^                         |        \
                     |                    approve     reject (reason
                     |                         |       mandatory)
                     +--------- rejected ------+--------/
                                               v
                                           APPROVED --mark done (external
                                               |       ref)--> COMPLETED
  Any open state --(re-evaluation: no longer needs action)--> CLOSED_SUPERSEDED

  - take: a maker picks the case from the shared queue (assigns it to
    self). An Administrator can reassign.
  - submit: the maker chooses the ACTION and adds remarks, plus evidence
    where needed. The action is pre-filled from the rule (e.g. R05 ->
    RET 115). The maker can change it, e.g. to another RET reason (Q1,
    v3).
  - approve / reject: a checker. A rejection goes back to the maker with
    the reason.
  - mark done: the maker records the NPCI portal / CBS reference after
    doing it.
  - A "close without action" outcome (e.g. an R13 investigation found the
    payment on the next day's NPCI file) is also an action and is approved
    the same way.

Action types (pre-filled from the rule's action/response code):
  - DRC reply 102 / 103 / 104
  - TCC 102 / 103
  - RET <reason> (default 115)
  - Manual credit + RRC 501
  - RRC 501 without a new credit (R06b, evidence required)
  - Adjustment entry in CBS
  - Chargeback raise / accept
  - Refund customer (reversal)
  - Close without action (with finding)

--------------------------------------------------------------------------------
3. QUEUE, AGEING, ALERTS
--------------------------------------------------------------------------------
  - Queue order:
      - HIGH first, then overdue, then due date, then age.
      - R07x (>35-day chargeback) and anything overdue are flagged.
  - Filters: business date, status, priority, rule, overdue, assigned to
    me, awaiting my approval.
  - Due date / overdue come from the rule result (working days, 16:00
    cutoff for RET). Ageing buckets come from rule_engine.AgeingBucket.
  - Remarks: append-only comments on the case.
  - Alerts: IN-APP only in Phase 3 (queue flags, counts). Email needs the
    bank's mail server and is deferred.

--------------------------------------------------------------------------------
4. ROLES (Django groups)
--------------------------------------------------------------------------------
  Administrator   : manage users and roles, reassign cases, settings
  Operations User : view queue and results (upload / run as in Phase 1-2)
  Maker           : take, submit, add remarks, mark done
  Checker         : approve / reject
  Auditor         : read-only everything, incl. full case history and
                    activity log

A user may hold several roles (D3).

--------------------------------------------------------------------------------
5. AUDIT
--------------------------------------------------------------------------------
  - Every case change is an append-only CASE EVENT, which cannot be
    edited or deleted (same protection as the rule set). It records:
      - who and when
      - old -> new status
      - the action and its old -> new values
      - remarks and evidence
  - User activity log: login, logout and failed login (spec: user activity
    report, Phase 6).

--------------------------------------------------------------------------------
6. RE-RUNS
--------------------------------------------------------------------------------
Re-evaluating a date supersedes its rule results (Phase 2). A case is
keyed by business date + RRN, so it survives and links to the new
result.
  - Same rule: nothing changes.
  - Rule changed, case not yet approved: the case updates, and an event
    records the change.
  - Rule changed, case already APPROVED or COMPLETED: the case is FLAGGED
    for review, never silently changed.
  - No longer needs action: CLOSED_SUPERSEDED (an event is recorded),
    unless it was approved or completed, which is flagged instead.

7. CARRY-FORWARDS FROM PHASE 2
--------------------------------------------------------------------------------
  - R06b: decided (D4).
  - R07x "bring to the user's notice": handled by the in-app flag (section
    3).
  - Several Adjustment rows for one RRN: the case shows ALL overlay rows
    for the RRN and is flagged "multiple adjustment rows", so the maker
    sees each one.
  - Same payment on two days (R12 on D, R13 on D+1): the R13 case shows
    "an R12 case exists for this RRN on D-1" as an information hint only.
    No automatic linking, per v3.2. (See P5.)
  - Archival trigger: a business date is "complete" when it has no open
    cases. Archival of results/cases before match groups is designed
    here, but run later (P6).
  - Code-table / rule changes need authorised approval (spec): see P3.

  P1 Cases = results with a due date (306 / 88 / 594 per date above),
     including the LOW DRC replies (R01: 143 on 14 Jul)?
     Recommendation: yes. They are an NPCI-portal action with a T+1
     deadline and NPCI penalties (Circular 42).

  P2 Bulk handling. Can a maker submit, and a checker approve, many cases
     at once?
     Recommendation:
       - Bulk is allowed for LOW / MEDIUM cases with the same action
         (e.g. 143 x "DRC reply 102").
       - HIGH cases (money moves) are handled one by one.

  P3 Rule and code-table changes under maker-checker.
     Recommendation:
       - Response-code edits (e.g. filling in the 7 unknown RET numbers)
         go through maker-checker in Phase 3.
       - Rule-set changes stay as versioned releases (as v3.2 was), with
         the owner's approval recorded.

  P4 Mitigation for self-approval (D3).
     Recommendation: allow it, but record a "self-approved" flag on the
     approval and list such items in the approval report, so the Auditor
     can see them.

  P5 Same payment on two days. Show the D-1 R12 hint on R13 cases?
     Recommendation: yes. It is display only and doesn't change v3.2's
     one-day rule.

  P6 Archival. Archive a date's cases and results when it has had no open
     cases for N days?
     Recommendation: design it now, choose N with ops, and build it at the
     end of Phase 3 if time allows.
